## 2026-10-07 DB·RLS 적용 기록

- 두 환경 모두 신규 표가 없음을 먼저 확인했습니다. Supabase는 V1~V17 Flyway 체크섬과 이력, 로컬은 Flyway 비활성·JPA update 구성을 확인했습니다.
- 두 DB의 public 스키마·데이터를 `.env.backups/yearly-curriculum-2026-10-06-B1JLdi/local-public.dump`, `supabase-public.dump`에 백업했습니다. Git 제외·파일 권한 600·PostgreSQL 18 복구 도구 읽기·주요 테이블 포함을 확인했습니다. 백업은 실제 복원하지 않았습니다.
- Supabase 기본 권한이 신규 표의 anon/authenticated 접근을 허용함을 발견했습니다. JDBC postgres 역할의 BYPASSRLS 확인 후 사용자에게 신규 두 표의 차단 승인을 받았습니다.
- V19__protect_yearly_curriculum_with_rls.sql을 추가했습니다. 기존 표나 기존 migration은 수정하지 않았습니다. 직접 클라이언트용 허용 정책은 없습니다.
- 접근 차단 테스트를 먼저 실행해 RLS 없는 상태의 직접 조회 노출로 실패함을 확인했고, V19 후 일반 역할의 조회·쓰기 차단과 별도 BYPASSRLS 백엔드 역할 CRUD 유지가 통과했습니다.
- Supabase에는 Flyway group=true로 V18·V19만 한 트랜잭션에 적용했습니다. 최종 버전 19, 두 migration 성공 및 전체 체크섬 검증 완료입니다. 로컬에는 동일 SQL을 트랜잭션으로 적용했으며 Flyway 이력을 새로 만들지 않았습니다.
- 실제 Supabase 역할별 접근은 임시 음수 ID의 새 표 검증 행으로 확인한 후 전체 롤백했습니다. 기존 과목 등 다른 표에 검증 행을 넣지 않았고 identity sequence도 사용하지 않았습니다. JDBC 조회와 backend 역할의 신규 표 생성·조회·수정·삭제, anon/authenticated 차단이 확인됐습니다.
- 두 DB 모두 새 표·제약·RLS 검증 통과, 최종 curriculum/curriculum_course 행 수는 0입니다. 기존 8개 표의 적용 전후 행 수·데이터 해시는 동일합니다. 기존 데이터와 Docker volume은 삭제하지 않았습니다.
- V19 추가 후 backend 전체 `./scripts/verify` 통과. 신규 접근 차단 회귀 테스트와 기존 성적 보존 테스트를 포함합니다.
